## Giving photographs the space

The archive supports three ways of browsing: scanning the collection, viewing a
photograph at scale, and following colour relationships. I kept persistent controls
to a minimum so each view could give most of its space to the photographs. A dense
index lets you scan the collection before choosing an image.

## Navigating by colour

Each photograph starts with suggestions based on its overall palette. Selecting a
swatch changes the suggestions to photographs with a nearby colour. This gives
visitors another route through the archive without a separate search interface.

During upload, the [current analyser](https://github.com/TheTexta/elliotmairet/blob/aef9eb2cc1cde3b9c79e738fd27ed34ddc03c74a/lib/palette/analyse-buffer.ts)
auto-orients the original and samples it at a maximum 256px longest side.
Modified median cut (MMCQ) produces up to 64 candidates; selection favours
supported, vibrant and perceptually distinct colours in OKLab. It returns **up
to five genuine sampled swatches**. Flat or near-monochrome photographs can have
fewer: no replacement colours are invented.

The illustration uses that production sampler and analyser on the same golden-leaves
original, [frozen locally on 23 November 2026](/projects/elliot-mairet/palette-extraction/mmcq-v1/recording.json).
Its five swatches remain in the
model's selection order. Population weights are calculated separately by assigning
every sampled pixel to its nearest selected swatch; they do not determine that order.

## Composing the archive

The current homepage groups photographs into recurring colour neighbourhoods.
I use a deterministic [masonry planner](https://github.com/TheTexta/elliotmairet/blob/aef9eb2cc1cde3b9c79e738fd27ed34ddc03c74a/lib/photographs/plan-colour-masonry.ts)
that balances palette relationships with uncropped image dimensions and patch
area, rather than placing every warm photograph in one block. Mobile and desktop
plans are rendered on the server, so hydration does not rearrange the archive.
This is a generated composition, not a saved curatorial order: adding photographs
can move existing ones.

Pages and palette JSON are cached; admin changes invalidate the relevant cache
tags. The browser reuses that palette data for colour matching while the homepage
composition refreshes with catalogue updates. This separates layout and discovery
from image analysis: selecting a colour does not rerun the extractor.

## Adding new work

A private admin area handles uploads, photograph details, and site text. The server
validates uploaded image content before publication, with colour analysis built
into that workflow.

An image can be accepted even if its publication response never reaches the
browser. Restarting the entire upload could then create a second photograph. I
separated preparation, file transfer, and publication in the [upload controller](https://github.com/TheTexta/elliotmairet/blob/aef9eb2cc1cde3b9c79e738fd27ed34ddc03c74a/lib/photographs/upload.ts).
After transfer, the controller retains the original paths and metadata so a retry
resends the same publication request instead of uploading another object.

The [retry regression tests](https://github.com/TheTexta/elliotmairet/blob/aef9eb2cc1cde3b9c79e738fd27ed34ddc03c74a/lib/photographs/upload.test.mjs)
simulate a lost or malformed response and assert that the next request has exactly
the original publication payload, even if form values have changed. A separate
case checks that a failed transfer restarts preparation rather than publishing an
incomplete object. These tests isolate the client controller with request adapters;
they do not exercise the storage and database services together.

Supabase holds photograph metadata and admin authentication; Cloudflare R2 stores
the originals. The server validates image content and publishes metadata and
palette data through the authenticated workflow. Elliot can add work without a
site deployment.

## Changing the palette model

The earlier extractor used OKLab k-medoids; its [historical recording](/projects/elliot-mairet/palette-extraction/recording.json)
remains unchanged. Replacing it meant changing stored palette data, not just
deploying new code. At the **5 November 2026 palette-only checkpoint**, the
[rollout record](https://github.com/TheTexta/elliotmairet/blob/aef9eb2cc1cde3b9c79e738fd27ed34ddc03c74a/docs/palette-extraction.md#production-catalogue-backfill--2026-11-05)
documents 271 checksum-verified originals, unchanged photograph rows and original
objects after the backfill, and preserved gallery ordering and column geometry at
1440px and 390px. These checks describe that dated palette-only release, before
the later colour-neighbourhood layout. Apply and exact rollback were rehearsed in
isolated PostgreSQL, not by rolling production back.

## What remains to learn

The delivered archive connects a broad index, individual photographs, and palette
navigation to one publishing workflow. The remaining questions are where Elliot
encounters friction while publishing and whether visitors find colour suggestions
useful. The implementation, controller tests and controlled-change checks do not
answer those questions; I have not measured them here.
