Comparing resale listings means working with inconsistent information. The same
item can appear under different titles, photographed against different backgrounds.
Conversely, two items can look alike while differing in product type or brand.
A useful comparison needs both the listing's description and its appearance.

I extended Grailed Plus with cross-market comparison and local image matching,
alongside price history, currency conversion and interface customization. Its
price-history functionality originated in
[RVRX/grailed-plus](https://github.com/RVRX/grailed-plus). My comparison work
centres on finding plausible candidates, refining their order and keeping the
results usable when a slower stage fails.

## Combining metadata and image similarity

The first pass uses the active listing's title, product type, brand and available
marketplace details to retrieve and rank candidates. Results are divided into
confidence groups so stronger product evidence takes precedence over a merely
similar photograph.

The second pass uses **MobileCLIP-S1** to represent images as numerical vectors.
Comparing these embeddings provides an additional signal about visual similarity.
I apply that signal to a bounded shortlist rather than running image inference
across every possible result.

Visual scores refine the order **within confidence groups**. They cannot move a
candidate from a weaker group ahead of a stronger one. This preserves the
metadata ranking's structure while allowing appearance to distinguish candidates
with comparable product evidence.

These groups express the application's ranking rules. Whether they correspond
well to the items a buyer considers comparable needs evaluation against human
judgments.

## Returning results before refinement finishes

Image inference introduces another model to load and another stage that can
take time or fail. I keep it outside the critical path for displaying the first
results.

Metadata matches render first. **ONNX Runtime runs image inference in an extension
worker**, and the visible ranking updates as scores arrive. Refinement has a
time budget; if it fails or runs out of time, the metadata results remain
available.

This makes the image stage an optional refinement of an existing result set.
It also avoids making one slow or unavailable stage determine whether the
comparison panel can show anything useful.

## Dividing work between the extension and gateway

The extension reads the active Grailed listing, presents results and computes
image embeddings locally. Marketplace retrieval still uses network requests.
Depop retrieval runs from the browser; eBay requests pass through a separate
Node.js gateway.

The gateway keeps eBay API credentials out of the distributed extension and
handles OAuth token reuse, category resolution, and text and image searches.
Category resolution and image search supplement the text search. If either
fails, text results remain available.

Local embedding inference and remote image search are separate operations.
An eBay image query can send listing-image data through the gateway. Keeping
inference on-device therefore does not make the complete comparison workflow
local.

Because the gateway can fetch images, its network boundary needs its own
controls. Image retrieval is restricted to approved marketplace hosts, rejects
redirects and enforces a download-size limit. Gateway tests exercise those
restrictions separately from the extension's ranking and interaction tests.

## Keeping results attached to the active listing

A buyer can navigate to another listing while a comparison is still running.
If listing A's image scores arrive after listing B has opened, they must not
reorder B's results.

The comparison controller invalidates obsolete requests and applies refinements
only to the active request. Its regression tests cover late results from an
earlier listing, scores arriving before refinement completes, exhaustion of the
time budget, and preservation of confidence groups during reordering.

The streaming case matters because a final-state assertion alone could pass
even if the interface waited for the entire refinement step. The test checks
that scores affect visible results before the refinement promise resolves,
protecting the progressive behaviour the interface depends on.

## Presenting price context

The extension also brings price history and currency conversion into the
listing page. Price history requires care because the available data establishes
the order of historical prices without providing an exact timestamp for every
change. The chart labels interpolated dates as estimates.

That distinction affects how someone reads a price change. An estimated date
should not appear to establish precisely when a seller changed the price.

## Demonstrating the product and evaluating the ranking

The [product page](/grailed-plus) reuses the extension's renderer, styles,
currency helpers and theme engine. Its interactive examples use deterministic
sample listings and simulated transitions, so visitors can inspect the
interface without installing the extension. The examples do not retrieve live
marketplace results.

The photo-only comparison above replays real MobileCLIP-S1 scores recorded with
the production ONNX worker, using descriptive sample metadata and licensed
photographs. It demonstrates the ranking change, not measured inference latency
or evidence of improved relevance across a representative catalogue.

The next evaluation should compare metadata-only ranking with image refinement
on a representative set of listings and independently judged matches. It should
also measure time to preliminary results and refinement behaviour across devices.
That would establish whether the additional image stage produces better
comparisons, and what it costs the browsing experience.

### Implementation scope

The architecture and tests described here refer to the implementation reviewed
in October 2026. The application source is private, and a particular Chrome Web
Store package needs separate version verification. Firefox build support does
not establish a Firefox store release.

Gateway tests use controlled inputs. Live marketplace compatibility and deployed
access controls require their own checks; the sample-data demos and offline
tests do not establish those properties.
